## D-001: Использование MongoDB вместо PostgreSQL и гибридная модель данных

- **Дата:** 2026-10-15
- **Статус:** Принято
- **Контекст:** Исходное ТЗ (раздел 6) составлено под классическую реляционную модель (PostgreSQL, 3NF). Однако для MVP зафиксирован стек MongoDB 7 + Mongoose 8.
- **Решение:** Применяется гибридный подход: ссылочная целостность через `ObjectId` используется там, где сущности живут самостоятельной жизнью (категории, бренды, товары, пользователи, отзывы), а встраивание (embedding) — для неизменяемых снимков состояния на момент совершения операции (снимок товаров, цен, адреса доставки и контактов в заказе `Order`).
- **Причина:** Устраняет необходимость сложных джойнов и блокировок при формировании истории заказов, защищает заказ от изменений цен и атрибутов товаров задним числом, соответствует паттернам документоориентированных баз данных.
- **Альтернативы:**
  1. Полная нормализация (ссылки на все справочники): отклонено из-за риска мутации исторических данных заказа при изменении товаров/адресов.
  2. Полное встраивание: отклонено из-за дублирования каталога и потери целостности категорий/брендов.
- **Связанные задачи:** T00, T01, T06; req 62.

## D-002: Базовый стек проекта и архитектура приложения

- **Дата:** 2026-10-15
- **Статус:** Принято
- **Контекст:** Требуется современная платформа для интернет-магазина с высокой скоростью загрузки, SSR/SSG для SEO и строгой типизацией.
- **Решение:** Next.js 14+ (App Router), React 18, TypeScript в strict-режиме, Tailwind CSS + shadcn/ui, Vitest для unit-тестов бизнес-логики.
- **Причина:** App Router обеспечивает гибридный рендеринг (SSR для страниц каталога и товаров, клиентские компоненты для корзины и интерактивных форм), единый стек фронтенда и бэкенда (Route Handlers), быстрый запуск без оверхеда контейнеризации в MVP.
- **Альтернативы:** Pages Router (устаревает), отдельный Express/NestJS бэкенд (усложняет развертывание и дублирует типы для MVP).
- **Связанные задачи:** T00; req 1, 7, 9.

## D-003: Кэширование подключения к MongoDB через глобальный Mongoose-клиент

- **Дата:** 2026-10-15
- **Статус:** Принято
- **Контекст:** В среде Node.js с поддержкой HMR (Next.js development) и serverless/edge-подобными вызовами Route Handlers каждый перезапуск модуля или входящий запрос может порождать новое соединение к MongoDB, исчерпывая лимит соединений (особенно на Atlas M0 с лимитом 500 соединений).
- **Решение:** Реализован паттерн глобального кэширования `globalWithMongoose.mongoose = { conn, promise }` в модуле `src/lib/db.ts`.
- **Причина:** Позволяет повторно использовать существующий коннект между запросами и hot-reload, гарантируя одно активное подключение к пулу.
- **Альтернативы:** Вызов `mongoose.connect()` внутри каждого Route Handler без кэширования (приводит к connection leak).
- **Связанные задачи:** T00, T01; req 1.

## D-004: Централизованная обработка ошибок и единый формат ответов API

- **Дата:** 2026-10-15
- **Статус:** Принято
- **Контекст:** Раздел 6 AGENT_SPEC.md требует строгий формат ошибок: `{ error: { code: string, message: string, details?: any } }`.
- **Решение:** Создана иерархия классов в `src/lib/errors.ts` (`AppError`, `ValidationError`, `NotFoundError`, `UnauthorizedError`, `ForbiddenError`, `ConflictError`, `InternalError`) и централизованная функция-обработчик `handleError(error: unknown)`.
- **Причина:** Гарантирует единый формат ошибок API для фронтенда, корректные HTTP-статусы, предотвращает утечку стектрейсов внутренних исключений клиенту.
- **Альтернативы:** Ручная обработка `try/catch` в каждом роуте с произвольным JSON (приводит к рассогласованию API).
- **Связанные задачи:** T00; req 1.

## D-005: Использование pnpm в качестве единого пакетного менеджера проекта

- **Дата:** 2026-10-15
- **Статус:** Принято
- **Контекст:** В проектах на Next.js с развитым стеком зависимостей стандартный npm расходует значительный объем дискового пространства из-за плоского дублирования `node_modules` и подвержен фантомным зависимостям (phantom dependencies).
- **Решение:** Проект полностью переведен на использование `pnpm` (`pnpm-lock.yaml`, `pnpm-workspace.yaml`). Все скрипты и зависимости управляются строго через `pnpm` (`pnpm dev`, `pnpm build`, `pnpm typecheck`, `pnpm lint`, `pnpm test`, `pnpm seed`).
- **Причина:**
  1. Строгая изоляция зависимостей исключает случайный импорт транзитивных библиотек, не объявленных в `package.json`.
  2. Высокая скорость установки и экономия диска за счет контентно-адресуемого хранилища hard-линков.
  3. Детерминированное воспроизведение дерева зависимостей через `pnpm-lock.yaml`.
- **Альтернативы:**
  1. `npm`: плоская структура `node_modules`, риск фантомных зависимостей, более медленный `npm install`.
  2. `yarn`: классический v1 устарел, Berry требует сложной настройки PnP для совместимости с Next.js.
- **Связанные задачи:** T00; req 1.

## D-006: Целочисленное хранение денежных величин в копейках и идемпотентный сид

- **Дата:** 2026-10-15
- **Статус:** Принято
- **Контекст:** Хранение денежных сумм в формате чисел с плавающей точкой (IEEE 754 float) приводит к ошибкам округления при операциях сложения, вычитания процентов и списания (например, `0.1 + 0.2 !== 0.3`). Также при повторном развертывании или локальной разработке скрипт сида не должен падать с ошибками дублирования уникальных ключей.
- **Решение:**
  1. Все денежные поля (`price`, `discountPrice`, `delivery.price`, `totalAmount`, `discountAmount`, `deliveryCost`, `finalAmount`) строго типизированы и валидируются как целые неотрицательные числа в копейках (`Number.isInteger`).
  2. Скрипт `scripts/seed.ts` построен на операциях `findOneAndUpdate` с флагом `{ upsert: true }` по уникальным ключам (`slug` для категорий и брендов, `sku` для товаров, `code` для доставки и промокодов), что гарантирует полную идемпотентность.
- **Причина:** Финансовая точность на уровне базы данных и API, отсутствие дубликатов при многократном вызове `pnpm seed`.
- **Альтернативы:**
  1. Хранение цен в рублях с типом Decimal128 (сложнее обрабатывать в JS/JSON и клиентских библиотеках).
  2. Полная очистка базы (`deleteMany({})`) перед сидом (приводит к случайному удалению пользовательских данных и сессий при перезапуске).
- **Связанные задачи:** T01, T06, T07; req 2, 3, 5, 11, 60.

## D-007: Аутентификация, ролевая модель (RBAC) на Better Auth и соблюдение 152-ФЗ

- **Дата:** 2026-10-15
- **Статус:** Принято
- **Контекст:** Требуется защищенная система управления сессиями, разграничение ролей (`customer | manager | admin`), соблюдение 152-ФЗ (обязательное согласие на обработку ПДн при создании учетной записи), предотвращение перебора учетных записей (enumeration attacks) и строгая валидация прав на сервере.
- **Решение:**
  1. Используется библиотека Better Auth с адаптером `mongodbAdapter` и плагином `admin` (роли `customer`, `manager`, `admin`; роль по умолчанию — `customer`).
  2. Схема пользователя расширена полями `phone`, `assignedCategoryIds[]`, `consents`, `deletedAt`.
  3. Проверка согласия на обработку ПДн и валидация пароля (не менее 8 знаков, латинские буквы и цифры) вынесены в серверный хук `before` (`/sign-up/email`), что исключает регистрацию в обход фронтенда.
  4. Сообщение об ошибке входа унифицировано до «Неверный логин или пароль» независимо от того, существует ли пользователь в базе (защита от перебора email), и включен rate limit на эндпоинт `/sign-in/email`.
  5. Проверка сессий и прав доступа выполняется строго на сервере в Server Components / Layouts через `src/lib/rbac.ts` (`requireAuth()`, `requireRole()`), а для API роутов — через `requireApiAuth()`, `requireApiRole()`.
- **Причина:** Исключение самописного криптографического кода, надежное хранение хэшей, защита от утечек метаданных пользователей, соответствие законодательству РФ по персональным данным.
- **Альтернативы:**
  1. Собственная реализация на JWT в cookie: высокая вероятность ошибок при инвалидации сессий, ротации и CSRF.
  2. NextAuth (Auth.js v5): усложненная конфигурация RBAC, отсутствие готового admin-плагина с блокировками и управлением ролями.
- **Связанные задачи:** T02, T08, T09, T10, T11; req 9, 10, 31.

## D-008: Серверная фильтрация каталога, древовидные категории и гибридный поиск по SKU и тексту

- **Дата:** 2026-10-15
- **Статус:** Принято
- **Контекст:** Требуется обеспечить высокую производительность каталога при одновременной фильтрации по нескольким параметрам (категория, бренд, цена, сортировка, пагинация) и надежный поиск как по префиксу/полному коду артикула (SKU), так и по полнотекстовому индексу (title, description), а также включение товаров дочерних категорий при выборе родительской категории.
- **Решение:**
  1. Серверная фильтрация в `services/catalog.service.ts`: эндпоинты `GET /api/categories`, `GET /api/products`, `GET /api/products/[slug]`.
  2. Фильтрация по категории автоматически находит саму категорию и всех её потомков в дереве через BFS-обход по `parentId`, передавая массив идентификаторов в `{ categoryId: { $in: categoryIds } }`.
  3. Поиск `q` комбинирует префиксное регулярное выражение по полю `sku` (`^KB-...`) и оператор полнотекстового поиска `$text: { $search: q }` через `$or`.
  4. Строгая валидация входящих query-параметров через Zod (`getProductsQuerySchema`): приведение типов строк к числам, валидация `priceMin <= priceMax`, ограничение максимального `limit` до 100 товаров на страницу, безопасная обработка массивов и списков брендов через запятую.
  5. В выдачу товаров всегда включаются только опубликованные и неудаленные товары (`isPublished: true, deletedAt: null`).
- **Причина:** Предотвращение передачи избыточных данных клиенту, защита базы от DoS-запросов с невалидными или гигантскими лимитами пагинации, точное соответствие ожиданиям покупателей при поиске артикулов и категорий.
- **Альтернативы:**
  1. Фильтрация на стороне клиента: отклонено, так как не масштабируется на большие объемы каталога и противоречит правилам AGENT_SPEC.
  2. Использование внешнего поискового движка (Elasticsearch): отклонено согласно разделу 8 AGENT_SPEC (вне MVP).
- **Связанные задачи:** T03, T04; req 2, 3, 4, 5.

## D-009: Гибридная архитектура каталога (SSR + мягкая синхронизация фильтров через URL без перезагрузки) и Schema.org Product

- **Дата:** 2026-10-16
- **Статус:** Принято
- **Контекст:** Требуется обеспечить полноценный серверный рендеринг (SSR) страниц витрины, каталога и карточки товара для высокого SEO-рейтинга и соответствия критерию Lighthouse Performance ≥ 80, при этом интерактивные манипуляции фильтрами (категория, бренды, диапазон цен, сортировка, пагинация) должны отражаться в URL без полной перезагрузки веб-страницы.
- **Решение:**
  1. Страницы витрины (`/`), каталога (`/catalog`), карточки товара (`/product/[slug]`) и информационные страницы (`/about`, `/delivery`, `/payment`, `/contacts`, `/not-found`) построены на серверных компонентах Next.js App Router (SSR) с прямой загрузкой через слой `src/services/catalog.service.ts`.
  2. Управление фильтрами и сортировкой вынесено в клиентский компонент `src/components/CatalogFilters.tsx`, который при изменении параметров выполняет `router.replace(`${pathname}?${params.toString()}`, { scroll: false })` внутри `useTransition`. Next.js обновляет серверные пропсы страницы через RSC Payload без полной перезагрузки документа браузером.
  3. Детальная карточка товара снабжена динамической генерацией OpenGraph метатегов (`generateMetadata`) и валидной JSON-LD микроразметкой стандарта Schema.org `Product` (`sku`, `brand`, `offers`, `aggregateRating`).
  4. Адаптивность от 320px до 1920px обеспечена мобильной выезжающей шторкой фильтров, гибкими CSS Grid сетками и touch-friendly элементами управления (интерактивный степпер и кнопка добавления в корзину с визуальным откликом).
- **Причина:** Высокая скорость первой отрисовки (FCP 0.6s, LCP 2.4s, Desktop Lighthouse Performance 87 баллов), сохранение истории браузера и возможность делиться прямыми ссылками на отфильтрованный каталог, идеальная индексация поисковыми роботами.
- **Альтернативы:**
  1. Чисто клиентский рендеринг через `useEffect` + `fetch`: отклонено из-за ухудшения SEO и задержки контента для поисковых ботов.
  2. Обычные ссылки с полной перезагрузкой страницы: отклонено из-за мерцания интерфейса и нарушения критерия приёмки T04.
- **Связанные задачи:** T04; req 1, 2, 3, 4, 5, 12, 13, 14, 15.

## D-010: Компоновка каталога (левая колонка фильтров + сортировка над товарами) и индикация активной навигации

- **Дата:** 2026-10-16
- **Статус:** Принято
- **Контекст:** В первоначальной верстке каталога возникали лишние боковые зазоры из-за дублирования flex-оберток, блок сортировки находился внутри левого сайдбара фильтров, а навигационные ссылки хедера не имели визуальной подсветки текущей страницы.
- **Решение:**
  1. Архитектура компоновщика: `CatalogFilters` выступает единой гибкой оберткой для контента каталога (`flex flex-col lg:flex-row gap-8 items-start w-full`), принимая карточки товаров и пагинацию через React `children`.
  2. Левая колонка (`aside w-64 shrink-0`): строго зафиксирована слева и содержит дерево категорий, фильтры брендов и диапазон цен с кнопками быстрого сброса.
  3. Правая колонка (`flex-1 w-full min-w-0`): в верхней части содержит выпадающий список «Сортировка» (`#catalog-sort`), выровненный по правому краю над карточками товаров, мобильную кнопку вызова фильтров и бейджи активных параметров; под ними рендерится адаптивная сетка карточек товаров и пагинация.
  4. Хедер (`Header.tsx`): переведен в клиентский компонент с вызовом `usePathname()`. Активный маршрут подсвечивается акцентным стилем (`font-semibold text-emerald-700 dark:text-emerald-400 bg-emerald-500/10 shadow-xs`), сохраняя ненавязчивый вид для неактивных пунктов.
- **Причина:** Устранение визуального шума, эргономичное соответствие отраслевым стандартам e-commerce витрин, моментальное понимание пользователем своего положения в структуре разделов магазина.
- **Альтернативы:**
  1. Выравнивание сортировки по центру сайдбара: отклонено, так как сортировка логически относится ко всей выборке карточек, а не к критериям отсева.
  2. Подсветка ссылок через CSS `:active`: отклонено, так как `:active` работает только во время нажатия мыши, а не отражает текущий URL приложения.
- **Связанные задачи:** T04 (фикс); req 1, 2.
