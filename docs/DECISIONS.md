## D-001: Использование MongoDB вместо PostgreSQL и гибридная модель данных

- **Дата:** 2026-10-15
- **Статус:** Принято
- **Контекст:** Исходное ТЗ (раздел 6) составлено под классическую реляционную модель (PostgreSQL, 3NF). Однако для MVP зафиксирован стек MongoDB 7 + Mongoose 8.
- **Решение:** Применяется гибридный подход: ссылочная целостность через `ObjectId` используется там, где сущности живут самостоятельной жизнью (категории, бренды, товары, пользователи, отзывы), а встраивание (embedding) — для неизменяемых снимков состояния на момент совершения операции (снимок товаров, цен, адреса доставки и контактов в заказе `Order`).
- **Причина:** Устраняет необходимость сложных джойнов и блокировок при формировании истории заказов, защищает заказ от изменений цен и атрибутов товаров задним числом, соответствует паттернам документоориентированных баз данных.
- **Альтернативы:**
  1. Полная нормализация (ссылки на все справочники): отклонено из-за риска мутации исторических данных заказа при изменении товаров/адресов.
  2. Полное встраивание: отклонено из-за дублирования каталога и потери целостности категорий/брендов.
- **Связанные задачи:** T00, T01, T06; req 62.

## D-002: Базовый стек проекта и архитектура приложения

- **Дата:** 2026-10-15
- **Статус:** Принято
- **Контекст:** Требуется современная платформа для интернет-магазина с высокой скоростью загрузки, SSR/SSG для SEO и строгой типизацией.
- **Решение:** Next.js 14+ (App Router), React 18, TypeScript в strict-режиме, Tailwind CSS + shadcn/ui, Vitest для unit-тестов бизнес-логики.

- **Альтернативы:** Pages Router (устаревает), отдельный Express/NestJS бэкенд (усложняет развертывание и дублирует типы для MVP).
- **Связанные задачи:** T00; req 1, 7, 9.

## D-003: Кэширование подключения к MongoDB через глобальный Mongoose-клиент

- **Дата:** 2026-10-15
- **Статус:** Принято
- **Контекст:** В среде Node.js с поддержкой HMR (Next.js development) и serverless/edge-подобными вызовами Route Handlers каждый перезапуск модуля или входящий запрос может порождать новое соединение к MongoDB, исчерпывая лимит соединений (особенно на Atlas M0 с лимитом 500 соединений).
- **Решение:** Реализован паттерн глобального кэширования `globalWithMongoose.mongoose = { conn, promise }` в модуле `src/lib/db.ts`.
- **Причина:** Позволяет повторно использовать существующий коннект между запросами и hot-reload, гарантируя одно активное подключение к пулу.
- **Альтернативы:** Вызов `mongoose.connect()` внутри каждого Route Handler без кэширования (приводит к connection leak).
- **Связанные задачи:** T00, T01; req 1.

## D-005: Использование pnpm в качестве единого пакетного менеджера проекта

- **Дата:** 2026-10-15
- **Статус:** Принято
- **Контекст:** В проектах на Next.js с развитым стеком зависимостей стандартный npm расходует значительный объем дискового пространства из-за плоского дублирования `node_modules` и подвержен фантомным зависимостям (phantom dependencies).
- **Решение:** Проект полностью переведен на использование `pnpm` (`pnpm-lock.yaml`, `pnpm-workspace.yaml`). Все скрипты и зависимости управляются строго через `pnpm` (`pnpm dev`, `pnpm build`, `pnpm typecheck`, `pnpm lint`, `pnpm test`, `pnpm seed`).
- **Причина:**
  1. Строгая изоляция зависимостей исключает случайный импорт транзитивных библиотек, не объявленных в `package.json`.
  2. Высокая скорость установки и экономия диска за счет контентно-адресуемого хранилища hard-линков.
  3. Детерминированное воспроизведение дерева зависимостей через `pnpm-lock.yaml`.
- **Альтернативы:**
  1. `npm`: плоская структура `node_modules`, риск фантомных зависимостей, более медленный `npm install`.
  2. `yarn`: классический v1 устарел, Berry требует сложной настройки PnP для совместимости с Next.js.
- **Связанные задачи:** T00; req 1.

## D-006: Целочисленное хранение денежных величин в копейках и идемпотентный сид

- **Дата:** 2026-10-15
- **Статус:** Принято
- **Контекст:** Хранение денежных сумм в формате чисел с плавающей точкой (IEEE 754 float) приводит к ошибкам округления при операциях сложения, вычитания процентов и списания (например, `0.1 + 0.2 !== 0.3`). Также при повторном развертывании или локальной разработке скрипт сида не должен падать с ошибками дублирования уникальных ключей.
- **Решение:**
  1. Все денежные поля (`price`, `discountPrice`, `delivery.price`, `totalAmount`, `discountAmount`, `deliveryCost`, `finalAmount`) строго типизированы и валидируются как целые неотрицательные числа в копейках (`Number.isInteger`).
  2. Скрипт `scripts/seed.ts` построен на операциях `findOneAndUpdate` с флагом `{ upsert: true }` по уникальным ключам (`slug` для категорий и брендов, `sku` для товаров, `code` для доставки и промокодов), что гарантирует полную идемпотентность.
- **Причина:** Финансовая точность на уровне базы данных и API, отсутствие дубликатов при многократном вызове `pnpm seed`.
- **Альтернативы:**
  1. Хранение цен в рублях с типом Decimal128 (сложнее обрабатывать в JS/JSON и клиентских библиотеках).
  2. Полная очистка базы (`deleteMany({})`) перед сидом (приводит к случайному удалению пользовательских данных и сессий при перезапуске).
- **Связанные задачи:** T01, T06, T07; req 2, 3, 5, 11, 60.

## D-007: Аутентификация, ролевая модель (RBAC) на Better Auth и соблюдение 152-ФЗ

- **Дата:** 2026-10-15
- **Статус:** Принято
- **Контекст:** Требуется защищенная система управления сессиями, разграничение ролей (`customer | manager | admin`), соблюдение 152-ФЗ (обязательное согласие на обработку ПДн при создании учетной записи), предотвращение перебора учетных записей (enumeration attacks) и строгая валидация прав на сервере.
- **Решение:**
  1. Используется библиотека Better Auth с адаптером `mongodbAdapter` и плагином `admin` (роли `customer`, `manager`, `admin`; роль по умолчанию — `customer`).
  2. Схема пользователя расширена полями `phone`, `assignedCategoryIds[]`, `consents`, `deletedAt`.
  3. Проверка согласия на обработку ПДн и валидация пароля (не менее 8 знаков, латинские буквы и цифры) вынесены в серверный хук `before` (`/sign-up/email`), что исключает регистрацию в обход фронтенда.
  4. Сообщение об ошибке входа унифицировано до «Неверный логин или пароль» независимо от того, существует ли пользователь в базе (защита от перебора email), и включен rate limit на эндпоинт `/sign-in/email`.
  5. Проверка сессий и прав доступа выполняется строго на сервере в Server Components / Layouts через `src/lib/rbac.ts` (`requireAuth()`, `requireRole()`), а для API роутов — через `requireApiAuth()`, `requireApiRole()`.
- **Причина:** Исключение самописного криптографического кода, надежное хранение хэшей, защита от утечек метаданных пользователей, соответствие законодательству РФ по персональным данным.
- **Альтернативы:**
  1. Собственная реализация на JWT в cookie: высокая вероятность ошибок при инвалидации сессий, ротации и CSRF.
  2. NextAuth (Auth.js v5): усложненная конфигурация RBAC, отсутствие готового admin-плагина с блокировками и управлением ролями.
- **Связанные задачи:** T02, T08, T09, T10, T11; req 9, 10, 31.

## D-008: Серверная фильтрация каталога, древовидные категории и гибридный поиск по SKU и тексту

- **Дата:** 2026-10-15
- **Статус:** Принято
- **Контекст:** Требуется обеспечить высокую производительность каталога при одновременной фильтрации по нескольким параметрам (категория, бренд, цена, сортировка, пагинация) и надежный поиск как по префиксу/полному коду артикула (SKU), так и по полнотекстовому индексу (title, description), а также включение товаров дочерних категорий при выборе родительской категории.
- **Решение:**
  1. Серверная фильтрация в `services/catalog.service.ts`: эндпоинты `GET /api/categories`, `GET /api/products`, `GET /api/products/[slug]`.
  2. Фильтрация по категории автоматически находит саму категорию и всех её потомков в дереве через BFS-обход по `parentId`, передавая массив идентификаторов в `{ categoryId: { $in: categoryIds } }`.
  3. Поиск `q` комбинирует префиксное регулярное выражение по полю `sku` (`^KB-...`) и оператор полнотекстового поиска `$text: { $search: q }` через `$or`.
  4. Строгая валидация входящих query-параметров через Zod (`getProductsQuerySchema`): приведение типов строк к числам, валидация `priceMin <= priceMax`, ограничение максимального `limit` до 100 товаров на страницу, безопасная обработка массивов и списков брендов через запятую.
  5. В выдачу товаров всегда включаются только опубликованные и неудаленные товары (`isPublished: true, deletedAt: null`).
- **Причина:** Предотвращение передачи избыточных данных клиенту, защита базы от DoS-запросов с невалидными или гигантскими лимитами пагинации, точное соответствие ожиданиям покупателей при поиске артикулов и категорий.
- **Альтернативы:**
  1. Фильтрация на стороне клиента: отклонено, так как не масштабируется на большие объемы каталога и противоречит правилам AGENT_SPEC.
  2. Использование внешнего поискового движка (Elasticsearch): отклонено согласно разделу 8 AGENT_SPEC (вне MVP).
- **Связанные задачи:** T03, T04; req 2, 3, 4, 5.

## D-009: Гибридная архитектура каталога (SSR + мягкая синхронизация фильтров через URL без перезагрузки) и Schema.org Product

- **Дата:** 2026-10-16
- **Статус:** Принято
- **Контекст:** Требуется обеспечить полноценный серверный рендеринг (SSR) страниц витрины, каталога и карточки товара для высокого SEO-рейтинга и соответствия критерию Lighthouse Performance ≥ 80, при этом интерактивные манипуляции фильтрами (категория, бренды, диапазон цен, сортировка, пагинация) должны отражаться в URL без полной перезагрузки веб-страницы.
- **Решение:**
  1. Страницы витрины (`/`), каталога (`/catalog`), карточки товара (`/product/[slug]`) и информационные страницы (`/about`, `/delivery`, `/payment`, `/contacts`, `/not-found`) построены на серверных компонентах Next.js App Router (SSR) с прямой загрузкой через слой `src/services/catalog.service.ts`.
  2. Управление фильтрами и сортировкой вынесено в клиентский компонент `src/components/CatalogFilters.tsx`, который при изменении параметров выполняет `router.replace(`${pathname}?${params.toString()}`, { scroll: false })` внутри `useTransition`. Next.js обновляет серверные пропсы страницы через RSC Payload без полной перезагрузки документа браузером.
  3. Детальная карточка товара снабжена динамической генерацией OpenGraph метатегов (`generateMetadata`) и валидной JSON-LD микроразметкой стандарта Schema.org `Product` (`sku`, `brand`, `offers`, `aggregateRating`).
  4. Адаптивность от 320px до 1920px обеспечена мобильной выезжающей шторкой фильтров, гибкими CSS Grid сетками и touch-friendly элементами управления (интерактивный степпер и кнопка добавления в корзину с визуальным откликом).
- **Причина:** Высокая скорость первой отрисовки (FCP 0.6s, LCP 2.4s, Desktop Lighthouse Performance 87 баллов), сохранение истории браузера и возможность делиться прямыми ссылками на отфильтрованный каталог, идеальная индексация поисковыми роботами.
- **Альтернативы:**
  1. Чисто клиентский рендеринг через `useEffect` + `fetch`: отклонено из-за ухудшения SEO и задержки контента для поисковых ботов.
  2. Обычные ссылки с полной перезагрузкой страницы: отклонено из-за мерцания интерфейса и нарушения критерия приёмки T04.
- **Связанные задачи:** T04; req 1, 2, 3, 4, 5, 12, 13, 14, 15.

## D-010: Компоновка каталога (левая колонка фильтров + сортировка над товарами) и индикация активной навигации

- **Дата:** 2026-10-16
- **Статус:** Принято
- **Контекст:** В первоначальной верстке каталога возникали лишние боковые зазоры из-за дублирования flex-оберток, блок сортировки находился внутри левого сайдбара фильтров, а навигационные ссылки хедера не имели визуальной подсветки текущей страницы.
- **Решение:**
  1. Архитектура компоновщика: `CatalogFilters` выступает единой гибкой оберткой для контента каталога (`flex flex-col lg:flex-row gap-8 items-start w-full`), принимая карточки товаров и пагинацию через React `children`.
  2. Левая колонка (`aside w-64 shrink-0`): строго зафиксирована слева и содержит дерево категорий, фильтры брендов и диапазон цен с кнопками быстрого сброса.
  3. Правая колонка (`flex-1 w-full min-w-0`): в верхней части содержит выпадающий список «Сортировка» (`#catalog-sort`), выровненный по правому краю над карточками товаров, мобильную кнопку вызова фильтров и бейджи активных параметров; под ними рендерится адаптивная сетка карточек товаров и пагинация.
  4. Хедер (`Header.tsx`): переведен в клиентский компонент с вызовом `usePathname()`. Активный маршрут подсвечивается акцентным стилем (`font-semibold text-emerald-700 dark:text-emerald-400 bg-emerald-500/10 shadow-xs`), для предотвращения переноса текста ссылок («О компании» на две строки) добавлен класс `whitespace-nowrap`, контейнеру навигации задан `shrink-0` и адаптивный `gap-1 lg:gap-1.5`.
- **Причина:** Устранение визуального шума, эргономичное соответствие отраслевым стандартам e-commerce витрин, моментальное понимание пользователем своего положения в структуре разделов магазина, сохранение опрятного однострочного вида пунктов меню.
- **Альтернативы:**
  1. Выравнивание сортировки по центру сайдбара: отклонено, так как сортировка логически относится ко всей выборке карточек, а не к критериям отсева.
  2. Подсветка ссылок через CSS `:active`: отклонено, так как `:active` работает только во время нажатия мыши, а не отражает текущий URL приложения.
- **Связанные задачи:** T04 (фикс); req 1, 2.

## D-011: Гибридное хранение корзины (localStorage / MongoDB), серверный расчёт цен, слияние и проверка складских остатков

- **Дата:** 2026-10-19
- **Статус:** Принято
- **Контекст:** Требуется реализовать хранение корзины для гостей (без создания сессии и лишних записей в БД) и для авторизованных пользователей (в БД MongoDB), обеспечить автоматическое слияние гостевой корзины при авторизации/регистрации с очисткой `localStorage`, гарантировать актуальность цен исключительно с сервера (клиенту не доверяем) и строго валидировать физические остатки товаров на складе (`stockQuantity`).
- **Решение:**
  1. **Гостевая корзина:** хранится в браузере в `localStorage` по ключу `kabachok_cart` строго в виде минимального массива `[{ productId: string, quantity: number }]`. Цены, скидки и метаданные на клиенте не сохраняются.
  2. **Обогащение гостевой корзины:** реализован эндпоинт `POST /api/cart/details`, который принимает сырые пары `{ productId, quantity }` и возвращает актуальные данные из MongoDB (цены в копейках, скидки, изображения, статус наличия и остаток) без записи в базу данных.
  3. **Серверная корзина пользователя:** модель `Cart` (`userId`, `items: [{ productId, quantity }]`). Поле `userId` в схеме определено с типом `Schema.Types.Mixed`, что обеспечивает полную совместимость со строковыми 32-символьными идентификаторами Better Auth без ошибок приведения `CastError` Mongoose.
  4. **Серверная валидация остатков (409 OUT_OF_STOCK):** при ручной установке количества (`PUT /api/cart`) сервер строго проверяет `item.quantity <= product.stockQuantity`. При превышении физического остатка выбрасывается `ConflictError` с кодом `OUT_OF_STOCK` (HTTP 409).
  5. **Алгоритм слияния корзин при входе:** при входе (`/login`) или регистрации (`/register`), а также при обнаружении перехода сессии в `CartProvider`, вызывается `POST /api/cart/merge` (или `PUT /api/cart` с флагом `merge: true`). Количества одинаковых товаров суммируются, но строго ограничиваются физическим остатком `Math.min(sum, product.stockQuantity)`. Товары с нулевым остатком отсекаются. Сразу после успешного слияния клиентский `localStorage` очищается.
  6. **UI корзины:** динамический бейдж количества в `Header.tsx`, интерактивная страница `/cart` со степпером, защитой от превышения остатков, расчётом промежуточной суммы (в копейках с форматированием в рубли) и наглядным блоком персональных рекомендаций на базе хитов продаж при пустой корзине.
- **Причина:** Абсолютная защита от фальсификации цен на стороне клиента (правило раздела 2 и 6 AGENT_SPEC), нулевая нагрузка на БД для неавторизованных посетителей, бесшовный пользовательский опыт при переходе из гостя в покупателя без потери добавленных товаров.
- **Альтернативы:**
  1. Хранение корзины гостя в Redis по куке сессии: отклонено согласно допущению A-14 (Redis исключён из MVP, оверхед инфраструктуры).
  2. Хранение снимков цен в localStorage: категорически отклонено правилами безопасности, так как клиентские данные подвержены манипуляциям и рассинхронизации при изменении цен в каталоге.
  3. Тип `userId: Schema.Types.ObjectId` в схеме `Cart`: отклонено, так как встроенный генератор Better Auth создает строковые ID (`32 chars`), что приводило к сбою валидации Mongoose.
- **Связанные задачи:** T05; req 6, 21.

## D-012: Транзакционное создание заказа, атомарное списание остатков с fallback-компенсацией, чистая финансовая логика в копейках и неизменяемые снимки

- **Дата:** 2026-10-20
- **Статус:** Принято
- **Контекст:** Процесс оформления заказа (`checkout`) требует высокой финансовой точности, защиты от состояния гонки (race conditions) при одновременной покупке одного и того же товара несколькими клиентами, корректного применения промокодов (процентных и фиксированных) с учетом срока действия и лимитов, возможности оформления для неавторизованных гостей (без принудительной регистрации) и сохранения неизменяемых снимков (snapshots) реквизитов, адреса и цен на момент покупки. При этом локальная разработка может вестись как на MongoDB Atlas (где replica set и транзакции доступны из коробки), так и на локальном standalone экземпляре без сконфигурированного replica set.
- **Решение:**
  1. **Транзакции и отказоустойчивый fallback:** `createOrder` пытается выполнить операцию внутри `session.withTransaction()`. Если среда не поддерживает транзакции (standalone MongoDB выдает ошибку `Transaction numbers are only allowed on a replica set member or mongos`), сервис прозрачно переключается на цепочку условных атомарных операций с блоком компенсации (rollback/compensation): при возникновении ошибки на любом шаге все списанные остатки товаров и инкременты промокодов возвращаются обратно через обратный `$inc`.
  2. **Атомарная защита от перепродажи (overselling):** списание остатка каждого товара выполняется через `Product.updateOne({ _id, stockQuantity: { $gte: qty } }, { $inc: { stockQuantity: -qty } })`. Если остатка недостаточно, операция не модифицирует документ, и выбрасывается `ConflictError` (`OUT_OF_STOCK`, HTTP 409).
  3. **Чистая финансовая логика в копейках (`lib/pricing.ts`):** все расчеты ведутся строго в целых копейках без округления float (`totalAmount`, `discountAmount`, `deliveryCost`, `finalAmount`). Базовая цена берется как `discountPrice ?? price` (A-08), промокод валидируется по статусу, датам, лимиту использований и минимальному чеку, после чего применяется поверх к сумме товаров. Итоговая формула: `finalAmount = totalAmount - discountAmount + deliveryCost` (A-07).
  4. **Атомарный инкремент использования промокода:** `PromoCode.updateOne({ _id, isActive: true, $or: [{ usageLimit: 0 }, { $expr: { $lt: ["$usedCount", "$usageLimit"] } }] }, { $inc: { usedCount: 1 } })`.
  5. **Неизменяемые снимки (snapshots) и поддержка гостей:** в модель `Order` встраиваются снимки контакта (`fullName, phone, email`), адреса доставки (`city, street, house, apartment, postalCode, comment`), выбранной доставки (`methodId, title, price`), товаров (`productId, sku, title, quantity, pricePerUnit, totalPrice`) и промокода. Поле `userId` является `nullable` для гостей (A-04). Для онлайн-оплаты формируется связанный `Payment(status: pending)`.
  6. **UI Checkout (`/checkout`):** одностраничный интерфейс с шагами контактов, адреса (с возможностью сохранения в профиль для авторизованных покупателей через `Address`), выбора способов доставки из БД (`GET /api/delivery-methods`), способов оплаты, промокода с предпросмотром скидки (`POST /api/promo/validate`), комментария и обязательного чекбокса согласия на обработку ПДн (152-ФЗ, валидация на сервере через Zod).
- **Причина:** Соответствие требованиям 11, 18, 31 и разделу 5.1.8 AGENT_SPEC, полная защита от финансовых ошибок и перепродажи товаров, гарантия неизменности истории заказов при мутациях каталога.
- **Альтернативы:**
  1. Вычисление цен на стороне клиента: категорически отклонено правилами безопасности раздела 2 AGENT_SPEC.
  2. Хранение ссылок `ObjectId` вместо снимков цен/адресов в `Order`: отклонено, так как изменение цены товара в каталоге исказило бы финансовые отчеты по ранее совершенным заказам.
  3. Отказ от fallback без replica set: привел бы к падению `createOrder` при локальном тестировании разработчиками без поднятого `rs0`.
- **Связанные задачи:** T06; req 11, 18, 31.

## D-013: Мок-провайдер онлайн-оплаты, криптографическая верификация вебхуков HMAC-SHA256, строгая идемпотентность и инкремент продаж

- **Дата:** 2026-10-20
- **Статус:** Принято
- **Контекст:** Требование №60 ТЗ предписывает интеграцию с платежными системами. Для MVP зафиксирован mock-провайдер с эмуляцией эквайринга. Требуется защитить публичный роут вебхука от несанкционированных вызовов (фальсификации статуса оплаты), исключить повторные списания и задвоение счетчиков продаж при дублировании входящих запросов, а также обеспечить корректную логику статусов при сбоях оплаты.
- **Решение:**
  1. **Интерфейс провайдера `PaymentProvider`:** абстрагирует создание сессии оплаты и валидацию входящих нотификаций (`createPayment`, `verifyWebhook`, `generateWebhookSignature`). Реализован класс `MockProvider`, эмулирующий поведение промышленных эквайрингов (YooKassa, Tinkoff, Stripe).
  2. **Криптографическая верификация HMAC-SHA256:** тело вебхука подписывается секретом `PAYMENT_WEBHOOK_SECRET` и передается в заголовке `x-payment-signature`. Сервер сравнивает дайджест с использованием `crypto.timingSafeEqual` для предотвращения атак по времени. Неподписанные или скомпрометированные запросы отклоняются с кодом 401 `INVALID_SIGNATURE`.
  3. **Строгая идемпотентность вебхуков:** при поступлении дублирующего вебхука с уже зафиксированным статусом (`payment.status === payload.status`), сервер возвращает ответ `{ ok: true, idempotent: true }` без повторной мутации заказа и без повторного начисления `salesCount`. События `failed`, пришедшие после `succeeded`, игнорируются.
  4. **Обновление статусов и складской аналитики:**
     - При статусе `succeeded`: `Payment.status = "succeeded"`, `paidAt = now`, `Order.status = "paid"`, добавляется запись в `order.statusHistory`, а у каждого товара в заказе атомарно инкрементируется счетчик покупок `Product.updateOne({ _id }, { $inc: { salesCount: quantity } })`.
     - При статусе `failed`: `Payment.status = "failed"`, а заказ сохраняется в статусе `"new"` без отмены резерва, позволяя покупателю повторить оплату через `POST /api/payments/retry`.
  5. **Тестовый UI эквайринга (`/pay/mock/[paymentId]`):** интерактивная страница эмуляции банка с визуализацией карты и двумя кнопками: успешного подтверждения и эмуляции отказа, инициирующими отправку реального подписанного вебхука через серверный мост.
  6. **Страница «Спасибо за заказ» (`/orders/[id]/success`):** отображает номер заказа, состав купленных товаров, адреса, финансовый итог и текущий статус оплаты с возможностью быстрой доплаты картой при статусах `pending` или `failed`.
- **Причина:** Максимальное приближение к промышленным стандартам безопасности интернет-эквайринга, надежность при сбоях сети и дублировании запросов, сохранение лояльности клиентов при случайных отказах карт.
- **Альтернативы:**
  1. Доверие клиентским колбэкам (редирект браузера со статусом `success`): категорически отклонено, так как клиент может легко сымитировать успешный редирект без факта оплаты.
  2. Использование открытого эндпоинта без HMAC: отклонено из-за уязвимости подделки оплат.
  3. Автоматическая отмена заказа сразу при первом сбое оплаты: отклонено, так как это вынуждало бы покупателя заново собирать корзину при банальной опечатке в CVC-коде.
- **Связанные задачи:** T07; req 60.

## D-014: Архитектура личного кабинета, строгая серверная защита IDOR (403/404), регламент отмены заказов (A-11), складская компенсация (A-06) и соблюдение 152-ФЗ

- **Дата:** 2026-10-20
- **Статус:** Принято
- **Контекст:** Личный кабинет покупателя (`/account`) включает разделы профиля, смены пароля, адресной книги, истории и состава заказов, повторения покупок, отмены заказов и управления согласиями. Требуется исключить несанкционированный доступ к чужим заказам и адресам (IDOR), обеспечить соблюдение 152-ФЗ при отзыве согласия на обработку ПДн, жестко ограничить клиентскую отмену заказа статусом `new` (A-11) с корректным возвратом зарезервированных остатков на склад (A-06) и реализовать безопасную досылку товаров из истории заказов в корзину с валидацией остатков.
- **Решение:**
  1. **Серверная защита владения данными (403/404 IDOR Protection):** Проверка принадлежности заказов и адресов авторизованному пользователю выполняется строго на сервере в `src/services/account.service.ts` и Route Handlers (`getUserOrderById`, `getUserAddressById`, `updateUserAddress`, `deleteUserAddress`, `cancelUserOrder`, `repeatUserOrder`). При попытке доступа к чужому ресурсу сервер немедленно возвращает `ForbiddenError` (HTTP 403) или `NotFoundError` (HTTP 404). Страницы `/account/**` защищены серверным guard `requireAuth`.
  2. **Регламент отмены заказа покупателем (A-11, A-06):** Кнопка и эндпоинт отмены доступны строго в статусе `new`. Заказы в статусах `paid`, `processing`, `shipped`, `completed` покупатель отменить не может (HTTP 409 Conflict). При отмене статус переводится в `cancelled`, в `statusHistory` фиксируется запись аудита, а списанные остатки товаров (`stockQuantity`) и счетчик использований промокода (`usedCount`) атомарно возвращаются обратно в базу данных.
  3. **Логика функции «Повторить заказ» (req 27):** Сервис проверяет товары из выбранного заказа на актуальную публикацию (`isPublished`, `!deletedAt`) и складской остаток (`stockQuantity > 0`). Доступные товары добавляются в серверную корзину (`Cart`) с ограничением физическим остатком `Math.min(orderQty, product.stockQuantity)`. Отсутствующие на складе товары корректно отсекаются, а пользователю выводится информативный отчет.
  4. **Управление согласиями и 152-ФЗ (req 30, 31):** Реализовано раздельное переключение согласий на маркетинг (`consents.marketing`) и на обработку ПДн (`consents.personalData`). Отзыв согласия на ПДн защищен обязательным модальным предупреждением об ограничении функций магазина (блокировка оформления заказов и сохранения адресов). Время изменения согласий протоколируется с точностью до миллисекунд.
  5. **Безопасная смена пароля и редактирование профиля (req 16, 17):** Смена пароля опирается на криптографию Better Auth (`auth.api.changePassword`) с проверкой текущего пароля (scrypt), валидацией сложности нового пароля (≥8 символов, буквы и цифры) и совпадением подтверждения. Редактирование личных данных (имя, телефон) типизировано и валидируется через Zod.
- **Причина:** Абсолютная защита конфиденциальности покупателей, строгое соблюдение законодательства РФ (152-ФЗ), целостность финансовой и складской модели интернет-магазина.
- **Альтернативы:**
  1. Фильтрация данных только на стороне клиента: категорически отклонено правилами безопасности раздела 2 AGENT_SPEC (клиенту не доверяем).
  2. Допущение отмены заказа покупателем в статусе `paid` или `processing`: отклонено согласно A-11, так как оплаченный заказ может находиться на этапе комплектации или доставки.
  3. Беспрепятственный отзыв согласия на ПДн без предупреждения: отклонено, так как 152-ФЗ накладывает функциональные ограничения на исполнение договора купли-продажи.
- **Связанные задачи:** T08; req 16, 17, 18, 19, 20, 26, 27, 30, 31.

## D-015: Админка товаров, строгое разграничение прав менеджеров по категориям (Category RBAC), мягкая деактивация и целостность цен/остатков

- **Дата:** 2026-10-20
- **Статус:** Принято
- **Контекст:** Требования №35–39 ТЗ регламентируют создание раздела управления товарами в админке (`/admin/products`) с проверкой ролей администратора и менеджера. Менеджер должен иметь возможность создавать, редактировать и деактивировать товары строго в рамках назначенных ему категорий (`assignedCategoryIds`), а администратор должен обладать полным доступом ко всем категориям. Требуется исключить манипуляции товарами чужих категорий в обход UI (через прямые API-запросы), поддержать целостность финансовых данных (цены в копейках), остатков на складе и обеспечить деактивацию без физического удаления из базы данных.
- **Решение:**
  1. **Серверная проверка прав по категориям (Category RBAC):**
     - В `src/services/admin-product.service.ts` реализована функция `checkCategoryAccess(user, categoryId)`. Для роли `admin` проверка всегда успешна. Для роли `manager` сверяется идентификатор категории со списком `user.assignedCategoryIds`. При несовпадении выбрасывается `ForbiddenError` (HTTP 403 Forbidden).
     - При выборке товаров (`getAdminProducts`) для менеджера автоматически накладывается фильтр `{ categoryId: { $in: assignedCategoryIds } }`. Если менеджер передает конкретный `categoryId` в query-параметрах, проверяется его принадлежность к назначенным; при попытке запросить чужую категорию возвращается HTTP 403.
     - При редактировании товара (`updateAdminProduct`) проверяются как текущая категория товара, так и целевая (при попытке смены категории). Менеджер не может отредактировать товар чужой категории и не может переместить товар из своей категории в чужую.
     - При деактивации (`deactivateAdminProduct` / `PATCH`) сервер аналогично проверяет права на категорию товара перед изменением `isPublished`.
  2. **Мягкая деактивация (`isPublished = false`):**
     - Товар не удаляется физически из коллекции MongoDB и не помечается `deletedAt`. Устанавливается `isPublished = false`, что моментально скрывает его из публичного каталога покупателей (`GET /api/products`), но оставляет доступным в админке для повторной активации менеджером или администратором.
  3. **Двухуровневая модель цен и остатков:**
     - В базе данных и на уровне API (`price`, `discountPrice`) цены хранятся строго в целых копейках (`Number.isInteger`, `min: 0`).
     - В UI панели администратора ввод и отображение производятся в удобном рублевом формате (`119 990.00 ₽`), а клиентский компонент производит точную конвертацию в копейки (`Math.round(priceRubles * 100)`).
     - Валидация Zod на сервере гарантирует, что `discountPrice` при наличии строго меньше базовой цены `price`, а `stockQuantity` является целым неотрицательным числом.
  4. **Транслитерация и уникальность идентификаторов:**
     - Разработана утилита `src/lib/slug.ts` с поддержкой транслитерации кириллических названий в URL-совместимые латинские slug-идентификаторы. Сервис проверяет уникальность `sku` и `slug` по базе данных, автоматически предотвращая коллизии.
  5. **Адаптивный интерфейс управления (`/admin/products`):**
     - Создан единый навигационный заголовок `AdminNav` с подсветкой текущего раздела, статусом роли и количеством назначенных категорий.
     - Разработан компонент `AdminProductsContent` с динамической фильтрацией по категории (для менеджера выводятся только разрешенные категории), бренду, статусу публикации, полнотекстовым поиском по SKU и названию, модальным окном создания/редактирования, управлением изображениями и характеристиками.
- **Причина:** Безусловное соблюдение правил безопасности (клиенту не доверяем, все RBAC-проверки на сервере), защита каталога от случайных повреждений менеджерами смежных отделов, строгое соблюдение финансовой целостности.
- **Альтернативы:**
  1. Фильтрация категорий только на клиенте через `disabled` в селекторах: категорически отклонено, так как позволяет злоумышленнику обойти ограничение через Postman/cURL.
  2. Физическое удаление товара при деактивации (`Product.deleteOne`): отклонено требованиями ТЗ и риском повреждения истории заказов (нарушение ссылочной целостности).
  3. Хранение цен в рублях с плавающей запятой (Float): отклонено из-за накапливающихся ошибок округления IEEE 754.
- **Связанные задачи:** T09; req 35, 36, 37, 38, 39.
