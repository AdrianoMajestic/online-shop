# Пояснительная записка: Задача T06. Оформление заказа и транзакционное создание

## Что сделано
- **Чистая финансовая логика (`src/lib/pricing.ts`):** расчет сумм строго в целых копейках (`calculateItemPrice`, `calculateItemsTotal`, `calculateOrderPrices`), валидация промокодов по датам (`validFrom`/`validTo`), статусу `isActive`, минимальному чеку `minOrderAmount` и лимиту использований `usageLimit`. Формула: `finalAmount = totalAmount - discountAmount + deliveryCost` (допущения A-07, A-08).
- **Транзакционный сервис оформления заказа (`src/services/order.service.ts`):**
  - Поддержка транзакций MongoDB (`session.withTransaction`) с надежным fallback-механизмом на условные атомарные операции `$inc` и компенсирующие откаты (компенсация остатков при сбое) для standalone MongoDB (п. 1 AGENT_SPEC.md).
  - Атомарное списание остатков: `updateOne({ _id, stockQuantity: { $gte: quantity } }, { $inc: { stockQuantity: -quantity } })`, предотвращающее состояние гонки (race conditions) при параллельных покупках.
  - Атомарный инкремент счетчика промокода: `updateOne({ _id, isActive: true, $or: [{ usageLimit: 0 }, { $expr: { $lt: ["$usedCount", "$usageLimit"] } }] }, { $inc: { usedCount: 1 } })`.
  - Генерация уникального человекочитаемого номера заказа (`KB-10001+`).
  - Фиксация неизменяемых снимков (snapshots): `contact`, `shippingAddress`, `delivery`, `items` (с ценой за единицу и суммой), `promo`.
  - Создание связанной записи `Payment` со статусом `pending` для онлайн-оплаты (`card_online`).
  - Очистка корзины в БД для авторизованного пользователя после успешного оформления.
- **Серверные Route Handlers:**
  - `GET /api/delivery-methods` — активные способы доставки с сортировкой по цене.
  - `POST /api/promo/validate` — проверка промокода с расчетом потенциальной скидки.
  - `POST /api/orders` — создание заказа (для гостя и авторизованного пользователя, валидация через Zod `createOrderSchema`, серверная проверка согласия 152-ФЗ).
  - `GET`, `POST /api/addresses` — получение и сохранение адресов доставки пользователя.
- **Одностраничный UI Checkout (`/checkout`):**
  - Секции: контактные данные, адрес доставки (выбор из сохраненных для авторизованных или ручной ввод с возможностью сохранения в профиль), способ доставки, способ оплаты, поле промокода с моментальной валидацией, комментарий к заказу, обязательный чекбокс согласия на обработку ПДн (152-ФЗ).
  - Поддержка оформления для гостя без принудительной регистрации (допущение A-04).
  - Автоматическая очистка клиентской корзины (`localStorage` / контекст) при успехе и редирект на экран оплаты или подтверждения.
- **Unit-тестирование:** 17 тестов на чистую логику ценообразования (`pricing.test.ts`) и 12 тестов на бизнес-логику заказов, валидацию и API-роуты (`order.test.ts`).

## Почему именно так
- Согласно разделу 2, 4 и 5 `AGENT_SPEC.md` и решениям D-001, D-006, D-012, все цены, скидки и итоговые суммы рассчитываются исключительно на сервере. Клиент передает только идентификаторы товаров, выбранную доставку и код промокода.
- Атомарное списание остатков с фильтром `$gte` гарантирует защиту от отрицательных остатков (overselling) даже в условиях высокой конкурентности запросов.
- Хранение снимков (snapshots) гарантирует неизменность реквизитов и сумм завершенного заказа при последующих изменениях каталога товаров или адресов пользователя.

## 3 вопроса для защиты с ответами
1. **Как система защищена от состояния гонки (race condition) и отрицательных остатков, если два покупателя одновременно закажут последний экземпляр товара?**
   *Ответ:* Защита построена на атомарном условном обновлении в MongoDB: `Product.updateOne({ _id: productId, stockQuantity: { $gte: requestedQty } }, { $inc: { stockQuantity: -requestedQty } })`. MongoDB блокирует конкретный документ на время операции записи. Первый запрос успешно спишет остаток (`matchedCount: 1, modifiedCount: 1`). Второй запрос не найдет документ, удовлетворяющий условию `stockQuantity >= requestedQty` (`matchedCount: 0`), операция не выполнится, транзакция откатится, а клиент получит понятную ошибку `ConflictError` (HTTP 409) с кодом `OUT_OF_STOCK` без нарушения целостности базы данных.
2. **Почему в заказе (`Order`) данные товаров, доставки и адреса хранятся встроенными снимками, а не ссылками на соответствующие коллекции?**
   *Ответ:* В интернет-магазине данные каталога и профиля мутируют со временем: администратор может изменить цену товара, переименовать его, удалить из ассортимента, служба доставки может поднять тарифы, а пользователь — отредактировать сохраненный адрес. Если хранить ссылки (`ObjectId`), заказ задним числом изменит свою стоимость и состав, что нарушит бухгалтерскую отчетность и юридические обязательства. Снимки (`snapshots`) фиксируют точное состояние на момент сделки.
3. **Как рассчитывается итоговая сумма заказа при комбинации скидочной цены товара, промокода и стоимости доставки?**
   *Ответ:* Расчет выполняется строго на сервере в `src/lib/pricing.ts`: сначала для каждого товара берется эффективная цена `calculateItemPrice` (`discountPrice ?? price`). Из суммы товаров формируется `totalAmount`. Затем валидируется промокод (активность, временные рамки, лимит использований и порог `minOrderAmount`). Промокод применяется поверх к сумме товаров, формируя `discountAmount` (процентный или фиксированный, но не более `totalAmount`). Итоговая сумма рассчитывается по формуле `finalAmount = totalAmount - discountAmount + deliveryCost` строго в целых копейках, предотвращая ошибки вычислений с плавающей запятой.
