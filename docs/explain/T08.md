# Пояснительная записка: Задача T08. Личный кабинет покупателя

## Что сделано
- **Разделы личного кабинета (`/account`)**:
  - **Профиль и безопасность (`/account`, `ProfileContent.tsx`)**: просмотр учетных данных (имя, телефон, подтвержденный email, дата регистрации, роль), редактирование профиля с валидацией Zod, смена пароля с проверкой текущего пароля (scrypt) и валидацией сложности (≥8 символов, буквы и цифры).
  - **Адресная книга (`/account/addresses`, `AddressesContent.tsx`)**: просмотр сохраненных адресов, добавление и редактирование через модальное окно с проверкой индексов и полей, удаление с подтверждением.
  - **История заказов (`/account/orders`, `OrdersList.tsx`)**: интерактивная фильтрация по статусам (все, новые, оплаченные, в обработке, доставляются, завершенные, отмененные), просмотр сумм, состава и дат.
  - **Детальная карточка заказа (`/account/orders/[id]`, `OrderDetailContent.tsx`)**: полный снимок состава товаров с артикулами и ценами на момент покупки, параметры доставки и получателя, финансовая детализация, интерактивный таймлайн смены статусов (`statusHistory`).
  - **Повторение заказа (`POST /api/orders/[id]/repeat`)**: добавление доступных товаров из исторического заказа в корзину пользователя с проверкой публикации и ограничением текущим остатком на складе (`stockQuantity`).
  - **Отмена заказа (`POST /api/orders/[id]/cancel`)**: отмена заказа доступна строго в статусе `new` (A-11) с автоматической складской компенсацией — возвратом зарезервированных остатков на склад и откат счетчика промокода (A-06).
  - **Управление согласиями по 152-ФЗ (`/account/consents`, `ConsentsContent.tsx`)**: раздельные переключатели согласия на маркетинговые рассылки и обработку ПДн с точной фиксацией времени. При попытке отозвать согласие на ПДн отображается предупреждающее модальное окно о блокировке оформления новых заказов и сохранения адресов.
- **Точечный фикс загрузки профиля и обработка рассинхронизации сессий (req 16)**:
  - **Полиморфный поиск по `ObjectId` и строковому `id` (`getUserProfile`, `updateUserProfile`, `updateUserConsents`)**: драйвер MongoDB чувствителен к типам. Если `_id` в коллекции `user` сохранен как `ObjectId`, то строковый `userId` из Better Auth теперь конвертируется в `new mongoose.Types.ObjectId(userId)` внутри условия `$or`, исключая ложные `NotFoundError`.
  - **Безопасный fallback в Server Components (`/account`, `/account/consents`)**: вызовы `getUserProfile` обернуты в `try/catch`. При отсутствии пользователя в БД или устаревшей сессии страница не выбрасывает 500, а плавно перенаправляет на `/login?reason=session_expired`.
  - **Инвалидация сессии в API и клиенте (`/api/user/profile`, `ProfileContent.tsx`)**: при `NotFoundError` Route Handler возвращает 401 и удаляет cookies Better Auth, а клиентский компонент вызывает `authClient.signOut()` и перенаправляет на страницу входа.
  - **Информативное уведомление на `/login`**: при наличии параметра `reason=session_expired` отображается аккуратный баннер об истечении сессии.
- **Серверная защита данных (IDOR Protection)**:
  - Проверка владения заказами и адресами реализована строго на сервере в `src/services/account.service.ts` и Route Handlers: при попытке открыть чужой заказ или изменить чужой адрес возвращается `403 Forbidden` или `404 Not Found`.

## Почему именно так
- Защита данных только на клиенте уязвима для подмены ID в URL (IDOR). Серверный слой `account.service.ts` гарантирует, что пользователь имеет доступ строго к своим записям.
- Ограничение отмены заказов статусом `new` (допущение A-11) предотвращает логистический коллапс при попытке отменить заказ, который уже оплачен, собран на складе или передан курьеру.
- При повторе заказа мы не дублируем исторические цены, а проверяем актуальное наличие в каталоге, защищая магазин от продажи несуществующих или подорожавших товаров по старой цене.
- При удалении пользователя или рассинхронизации сессии Better Auth приложение не должно падать с неперехваченным исключением: безопасный fallback очищает сессию и возвращает пользователя к экрану входа.

- `src/app/login/page.tsx` — страница входа с баннером об истекшей сессии (`reason=session_expired`).
- `src/app/account/orders/page.tsx`, `src/app/account/orders/[id]/page.tsx` — история и детальный просмотр заказов с историей статусов.

## 3 вопроса для защиты с ответами
1. **Как в личном кабинете предотвращается уязвимость IDOR (Insecure Direct Object Reference) при запросе чужого заказа?**
   *Ответ:* Идентификатор заказа (`id` или `number`) передается в эндпоинт `GET /api/orders/[id]`, где Route Handler извлекает сессию авторизованного пользователя (`session.user.id`). В сервисе `getUserOrderById` выполняется явная проверка: если `String(order.userId) !== String(userId)`, сервер выбрасывает исключение `ForbiddenError` (HTTP 403) либо `NotFoundError` (HTTP 404). Клиенту не доверяем, чужие данные не отдаются даже при знании прямого идентификатора заказа в базе.
2. **Почему покупатель может отменить заказ только в статусе «Новый» и что происходит со складом при отмене?**
   *Ответ:* Согласно допущению A-11, клиентская отмена ограничена статусом `new`, поскольку в статусах `paid`, `processing` и `shipped` заказ уже оплачен, скомплектован или находится у курьерской службы (в этих случаях отмена требует регламента возврата через менеджера). При отмене заказа в статусе `new` срабатывает компенсационная логика (A-06): количество каждого товара атомарно возвращается на склад через `Product.updateOne({ $inc: { stockQuantity: quantity } })`, а примененный промокод освобождается через декремент `usedCount`.
3. **Что происходит при рассинхронизации сессии Better Auth и записи пользователя в БД при переходе на `/account`?**
   *Ответ:* В `src/services/account.service.ts` метод `getUserProfile` производит сопоставление как по строковому `id`, так и по BSON `ObjectId`. Если запись пользователя в базе отсутствует (пользователь удален или сессия устарела), сервис генерирует `NotFoundError`. В серверном компоненте `/account` это исключение перехватывается, и пользователь безопасно перенаправляется на `/login?reason=session_expired`. В API эндпоинте `/api/user/profile` в ответ возвращается 401 с удалением сессионных cookie `better-auth.session_token`, а клиентский интерфейс очищает локальное состояние через `authClient.signOut()`, предотвращая 500 ошибку и падение страницы.
