# Пояснительная записка: Задача T02. Авторизация и роли (Better Auth)

## Что сделано
- Подключена библиотека Better Auth в `src/lib/auth.ts` с адаптером `mongodbAdapter`, плагином `admin` (роли `customer | manager | admin`, по умолчанию `customer`), провайдером `emailAndPassword` и расширенной схемой `additionalFields`: `phone`, `assignedCategoryIds[]`, `consents`, `deletedAt`.
- На сервере в хуке `before` реализована строгая валидация обязательного согласия на обработку ПДн (152-ФЗ) и сложности пароля (≥ 8 символов, включая буквы и цифры). Регистрация без согласия отклоняется на уровне API.
- Настроено единое сообщение об ошибке аутентификации «Неверный логин или пароль» в Route Handler `src/app/api/auth/[...all]/route.ts` и включен встроенный rate limit для защиты от подбора паролей.
- Создан модуль RBAC `src/lib/rbac.ts` с серверными хелперами `requireAuth()`, `requireRole()`, `requireApiAuth()`, `requireApiRole()`.
- Защищены маршруты `/account/**` (требуется сессия) и `/admin/**` (требуется роль `admin` или `manager`) проверками на сервере в Server Components Layouts.
- Созданы страницы входа `/login`, регистрации `/register`, личного кабинета `/account`, панели управления `/admin` и интерактивный компонент `UserNav` с меню профиля в хедере.
- Дополнен скрипт `scripts/seed.ts` идемпотентным созданием пользователей `admin@shop.test`, `manager@shop.test` (с 2 категориями) и `user@shop.test` (пароль `Passw0rd1`) через Better Auth API.
- Написаны unit-тесты `src/tests/auth.test.ts` (9 тестов проверки согласий, паролей, единой ошибки входа и RBAC-ограничений).

## Почему именно так
- Использование проверенной библиотеки Better Auth исключает уязвимости самописного кода сессий и паролей (CSRF, session fixation, timing attacks).
- Проверка согласия на 152-ФЗ на сервере гарантирует юридическую чистоту: пользователь не может быть зарегистрирован через прямой POST-запрос без согласия.
- Единый текст ошибки «Неверный логин или пароль» защищает от перебора существующих email-адресов (user enumeration).
- Серверная проверка ролей в layout предотвращает утечку служебного UI клиентам без соответствующих прав.

## Ключевые файлы
- `src/lib/auth.ts` — серверный инстанс Better Auth с плагином admin, additionalFields и хуками валидации.
- `src/lib/auth-client.ts` — клиентский инстанс Better Auth (`signIn`, `signUp`, `signOut`, `useSession`).
- `src/lib/rbac.ts` — функции защиты серверных маршрутов и API (`requireAuth`, `requireRole`).
- `src/app/api/auth/[...all]/route.ts` — Next.js Route Handler для аутентификации.
- `src/app/register/page.tsx` — страница регистрации с чекбоксом 152-ФЗ.
- `src/app/login/page.tsx` — страница авторизации.
- `src/components/UserNav.tsx` — адаптивное меню пользователя в шапке сайта.
- `scripts/seed.ts` — сид тестовых учетных записей администратора, менеджера и покупателя.
- `src/tests/auth.test.ts` — юнит-тесты валидации согласий, сложности паролей и RBAC.

## 3 вопроса для защиты с ответами
1. **Почему проверка согласия на обработку ПДн (152-ФЗ) реализована в хуке Better Auth на бэкенде, а не только на клиенте?**
   *Ответ:* Валидация только в форме на клиенте легко обходится прямым HTTP-запросом к `/api/auth/sign-up/email`. Реализация проверки в хуке `before` Better Auth гарантирует, что ни одна учетная запись не будет создана в базе данных без зафиксированного факта согласия (`consents.personalData.given === true`), что строго соответствует требованиям 152-ФЗ.
2. **Почему при неверном логине и неверном пароле возвращается одно и то же сообщение «Неверный логин или пароль»?**
   *Ответ:* Если сервер возвращает разные сообщения (например, «Пользователь не найден» против «Неверный пароль»), злоумышленник может использовать это для атаки перебора (user enumeration) и выяснить, какие email зарегистрированы в интернет-магазине. Единое сообщение и одинаковый код `INVALID_EMAIL_OR_PASSWORD` полностью скрывают факт наличия аккаунта.
3. **Как обеспечивается защита панели управления `/admin` от несанкционированного доступа?**
   *Ответ:* Защита реализована на уровне сервера в `src/app/admin/layout.tsx` с помощью `requireRole("admin", "manager")`. Проверка cookie-сессии и поля роли (`role`) выполняется в Server Component до рендеринга страницы. Неавторизованные пользователи перенаправляются на `/login`, а авторизованные пользователи с ролью `customer` перенаправляются на главную страницу с отказом в доступе.
