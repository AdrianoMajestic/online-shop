# Пояснительная записка: Задача T03. API каталога

## Что сделано
- Создан модуль валидации входящих параметров каталога `src/lib/validations/catalog.ts` на базе Zod: проверка поисковой фразы `q`, слага категории, списка брендов `brand`, диапазона цен `priceMin`/`priceMax` (с проверкой `priceMin <= priceMax`), сортировки `sort` (`popular | price_asc | price_desc | new | rating`) и пагинации `page`/`limit`.
- Создан сервисный слой `src/services/catalog.service.ts`:
  - `getCategoryTree()` — построение иерархического дерева видимых категорий (`isVisible: true`) с вложенными потомками;
  - `getCategoryAndDescendantIds()` — рекурсивный BFS-поиск идентификаторов заданной категории и всех её дочерних категорий любого уровня вложенности;
  - `getProducts()` — фильтрация, поиск и пагинация опубликованных и неудаленных товаров (`isPublished: true, deletedAt: null`) с оператором `$or` (префиксный SKU + полнотекстовый поиск `$text`);
  - `getProductBySlug()` — получение карточки товара по slug с populate категории и бренда (выбрасывает `NotFoundError`, трансформируемый в 404).
- Реализованы серверные Route Handlers:
  - `GET /api/categories` — возврат дерева категорий;
  - `GET /api/products` — возврат пагинированного списка товаров по контракту `{ items, page, limit, total }`;
  - `GET /api/products/[slug]` — детальная информация о товаре по slug.
- Написаны unit-тесты:
  - `src/tests/catalog-validation.test.ts` (5 тестов схемы валидации параметров);
  - `src/tests/catalog-routes.test.ts` (5 тестов route handlers, проверка контракта и обработки ошибок 400 и 404).
- Создан и выполнен скрипт ручной проверки на реальной базе данных `scripts/verify-catalog.ts`.

## Почему именно так
- Согласно разделу 3 AGENT_SPEC соблюдена слоистая архитектура: Route Handler → Zod-валидация → Service → Mongoose-модели. Бизнес-логика фильтрации и поиска изолирована в сервисе.
- Вся фильтрация, сортировка и пагинация выполняются строго на сервере, исключая передачу лишних данных на клиент.
- Поиск по категории включает всех потомков (например, выбор «Электроника» находит смартфоны и ноутбуки), что соответствует поведению современных e-commerce платформ.

## Ключевые файлы
- `src/lib/validations/catalog.ts` — Zod-схема валидации query-параметров каталога.
- `src/services/catalog.service.ts` — сервисные функции дерева категорий, поиска и выборки товаров.
- `src/app/api/categories/route.ts` — Route Handler `GET /api/categories`.
- `src/app/api/products/route.ts` — Route Handler `GET /api/products`.
- `src/app/api/products/[slug]/route.ts` — Route Handler `GET /api/products/[slug]`.

## 3 вопроса для защиты с ответами
1. **Как реализован поиск товаров по параметру `q` и почему используется гибридный подход?**
   *Ответ:* Поиск `q` в `services/catalog.service.ts` объединяет через оператор `$or` префиксное регулярное выражение по полю артикула `sku` (`^KB-...`, регистронезависимое) и оператор полнотекстового индекса `$text: { $search: q }` по полям `title` и `description`. Это позволяет пользователю мгновенно находить товары как по точному/частичному артикулу (например, `KB-APL`), так и по ключевым словам из названия и описания (например, `кофемашина` или `титановый`).
2. **Как работает фильтрация по категории при наличии вложенных подкатегорий?**
   *Ответ:* Функция `getCategoryAndDescendantIds(slug)` находит выбранную категорию по slug и с помощью BFS-обхода собирает её `_id`, а также идентификаторы всех её прямых и косвенных потомков по полю `parentId`. В результирующем запросе к MongoDB применяется фильтр `{ categoryId: { $in: categoryIds } }`. Таким образом, при выборе родительской категории («Электроника») в выдачу автоматически попадают товары всех её дочерних категорий («Смартфоны и гаджеты», «Ноутбуки и компьютеры»).
3. **Как обеспечивается защита от некорректных параметров и перегрузки базы данных в `GET /api/products`?**
   *Ответ:* Все входящие query-параметры валидируются Zod-схемой `getProductsQuerySchema`: строковые числа трансформируются в целые, проверяется условие `priceMin <= priceMax`, лимит пагинации принудительно ограничен диапазоном 1–100, а фильтр непубликованных и удаленных товаров (`isPublished: true, deletedAt: null`) жестко зафиксирован на сервере и не может быть переопределен клиентом.
