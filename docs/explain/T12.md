# Пояснительная записка: Задача T12. Журнал аудита

## Что сделано и почему
- **Сервис аудита (`src/services/audit.ts`, `src/lib/audit.ts`)**: Создан универсальный хелпер `audit(action, entity, entityId, meta, options)` с поддержкой 4 и 5 аргументов, а также утилита `getClientIp`.
- **Интеграция ключевых событий**: Вызовы `audit(...)` встроены в авторизацию (`user.login`), смену статусов заказов (`order.status_change`), изменение цен и остатков товаров (`product.price_change`, `product.stock_change`), деактивацию и удаление сущностей (`product.deactivate`, `category.delete`, `brand.delete`, `delivery_method.delete`, `promocode.deactivate/delete`), смену ролей (`user.role_change`) и блокировки (`user.ban/unban`).
- **Административный раздел (`/admin/audit`)**: Создана страница и API (`GET /api/admin/audit`), защищенные проверкой роли `admin` (`requireRole('admin')`), с фильтрацией по типам действий, сущностям, диапазону дат, текстовым поиском, пагинацией и просмотром полного контекста события (JSON meta).
- **Безопасность и надежность**: Сбои записи аудита не прерывают бизнес-транзакции пользователей; доступ закрыт для менеджеров и покупателей (HTTP 403).

## Ключевые файлы
- `src/models/AuditLog.ts` — Mongoose-схема с составными индексами и поддержкой смешанного идентификатора пользователя.
- `src/services/audit.ts`, `src/lib/audit.ts` — универсальный сервис записи и выборки логов с обогащением данных пользователей.
- `src/app/api/admin/audit/route.ts` — защищенный эндпоинт выборки журнала аудита.
- `src/components/admin/AdminAuditContent.tsx`, `src/app/admin/audit/page.tsx` — UI журнала с фильтрами и просмотром payload.
- `src/tests/audit.test.ts` — модульные тесты хелпера, интеграции событий и защиты эндпоинта.

## 3 вопроса для защиты с ответами
1. **Как обеспечивается независимость основных бизнес-операций от сбоев подсистемы аудита?**
   *Ответ:* Вызовы `audit(...)` в сервисах товаров, заказов, авторизации и пользователей выполняются асинхронно с перехватом ошибок через `.catch()`. Если в базе данных происходит временный сбой, ошибка логируется на сервере, но не отменяет успешное изменение статуса заказа, обновление товара или вход пользователя.
2. **Как реализовано определение IP-адреса инициатора события?**
   *Ответ:* Хелпер `getClientIp` анализирует заголовки входящего запроса: в первую очередь извлекается первый IP из цепочки прокси-серверов `x-forwarded-for`, затем проверяется `x-real-ip`, а при их отсутствии возвращается локальный fallback-адрес `127.0.0.1`.
3. **Каким образом разграничен доступ к журналу аудита между администратором и менеджером?**
   *Ответ:* Раздел `/admin/audit` и API `/api/admin/audit` строго ограничены ролью `admin` через серверные гарды `requireRole('admin')` и `requireApiRole(['admin'])`. Вкладка аудита скрыта из меню менеджера, а при прямом запросе менеджер получает редирект или ответ HTTP 403 Forbidden.
