# Пояснительная записка: Задача T09. Админка: товары

## Что сделано
- **Раздел управления товарами (`/admin/products`)**:
  - Список товаров с пагинацией, поиском по названию и артикулу (SKU), фильтрацией по категориям, брендам и статусу публикации (`isPublished`).
  - Создание нового товара: валидация Zod, генерация уникального латинского slug из русского названия (`slugify`), сохранение артикула (SKU), описания, фото и характеристик (`attributes`).
  - Редактирование товара: изменение цен, старой цены, остатка `stockQuantity`, категории, бренда, описания, изображений и атрибутов.
  - Деактивация товара: переключение `isPublished = false` без физического удаления из базы данных и без выставления `deletedAt`.
- **Серверное разграничение доступа (Category RBAC)**:
  - Менеджер видит и может редактировать товары *только* в назначенных категориях (`assignedCategoryIds`). При попытке менеджера запросить, создать, отредактировать или деактивировать товар чужой категории сервер возвращает `403 Forbidden`.
  - Администратор имеет полный доступ ко всем категориям и товарам каталога.
  - Менеджер не может переместить товар из своей категории в чужую (проверка обеих категорий).

## Почему именно так
- Защита прав выполняется строго на сервере в `src/services/admin-product.service.ts` и Route Handlers, исключая обход фильтров в UI через cURL/Postman.
- Цены хранятся в БД строго в копейках (целые числа), а конвертация в рубли производится на уровне UI.
- Деактивация через `isPublished = false` защищает ссылочную целостность исторических заказов.

- `src/services/admin-product.service.ts` — серверный сервис товаров и проверка прав `checkCategoryAccess`.
- `src/lib/validations/admin-product.ts` — Zod-схемы валидации запросов, создания и обновления товаров.
- `src/lib/slug.ts` — утилита транслитерации кириллицы в URL-совместимый латинский slug.
- `src/app/api/admin/products/route.ts`, `src/app/api/admin/products/[id]/route.ts` — API Route Handlers.
- `src/app/api/admin/categories/route.ts`, `src/app/api/admin/brands/route.ts` — справочники для админки.
- `src/app/admin/products/page.tsx`, `src/components/admin/AdminProductsContent.tsx` — UI админки товаров.
- `src/components/admin/AdminNav.tsx` — навигационный бар панели управления с индикацией роли.
- `src/tests/admin-products.test.ts` — 27 unit-тестов RBAC, валидации, транслитерации и Route Handlers.

## 3 вопроса для защиты с ответами
1. **Как технически реализовано разграничение доступа менеджеров к товарам по категориям (Category RBAC)?**
   *Ответ:* В модели пользователя Better Auth хранится массив `assignedCategoryIds`. На сервере в `admin-product.service.ts` функция `checkCategoryAccess` проверяет: если роль пользователя `manager`, идентификатор категории товара (`categoryId`) обязан входить в `user.assignedCategoryIds`. В противном случае сервер немедленно возвращает `ForbiddenError` (HTTP 403 Forbidden). Для роли `admin` проверка категории опускается (полный доступ). В списке товаров для менеджера автоматически накладывается фильтр `{ categoryId: { $in: assignedCategoryIds } }`.
2. **Что произойдет, если менеджер попытается сменить категорию товара на не назначенную ему?**
   *Ответ:* В методе `updateAdminProduct` выполняется двойная проверка: сначала проверяется текущая категория товара (может ли менеджер в принципе редактировать этот товар), а затем целевая категория из входящего запроса. Если менеджер пытается перенести товар в чужую категорию, сервер отклоняет запрос с ошибкой `403 Forbidden` («Доступ запрещен: категория товара не назначена менеджеру»), предотвращая утечку товаров из зоны ответственности.
3. **Чем деактивация товара отличается от мягкого удаления (soft delete) и почему выбрано именно это решение?**
   *Ответ:* Деактивация переключает флаг `isPublished = false`. При этом товар скрывается из публичного каталога покупателей (`GET /api/products`), но остается доступен в админке со статусом «Снят с продажи» и может быть в любой момент активирован обратно. Мягкое удаление устанавливает `deletedAt: new Date()`, помечая товар как удаленный из админки. Физическое же удаление (`deleteOne`) недопустимо, так как нарушило бы ссылочную целостность в оформленных заказах покупателей.
