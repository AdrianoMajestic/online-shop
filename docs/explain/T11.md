# Пояснительная записка: Задача T11. Админка: справочники, пользователи, доставка, промокоды

## Что сделано и почему
- **Справочники (`/admin/categories`, `/admin/brands`)**: Реализован CRUD категорий (иерархия, авто-slugify, сортировка, защита от удаления непустых веток/товаров) и брендов с подсчетом товаров.
- **Доставка и оплата (`/admin/delivery`)**: Управление тарифами доставки (в копейках) и переключение доступности способов оплаты `card_online` / `cod` (требования №50, 51).
- **Промокоды (`/admin/promocodes`)**: Процентные и фиксированные скидки, сроки действия, лимиты использований; деактивация вместо удаления для кодов, уже примененных в заказах.
- **Управление пользователями (`/admin/users`)**: Поиск, смена ролей (`customer | manager | admin`), бан с аннулированием сессий, назначение категорий менеджерам.
- **Защита прав (D-017)**: Все эндпоинты закрыты проверкой `requireRole('admin')` (менеджер получает 403). Действует строгая защита от самоблокировки: админ не может забанить себя или снять с себя роль admin.

## Ключевые файлы
- `src/services/admin-directory.service.ts` — бизнес-логика справочников, пользователей и защита от самоблокировки.
- `src/lib/validations/admin-directory.ts` — Zod-схемы валидации категорий, брендов, доставки, промокодов и пользователей.
- `src/app/api/admin/` (`categories`, `brands`, `delivery-methods`, `promocodes`, `payment-methods`, `users`) — API Route Handlers.
- `src/components/admin/` (`AdminCategoriesContent`, `AdminBrandsContent`, `AdminDeliveryContent`, `AdminPromocodesContent`, `AdminUsersContent`) — UI админки.
- `src/tests/admin-directories.test.ts` — 22 unit-теста валидации, CRUD, защиты от самоблокировки и RBAC (401/403/200).

## 3 вопроса для защиты с ответами
1. **Как технически реализована защита администратора от самоблокировки и потери прав доступа?**
   *Ответ:* В сервисе `admin-directory.service.ts` при вызове `updateAdminUserRole` и `toggleAdminUserBan` сервер проверяет ID и email текущего администратора из сессии. Если администратор пытается заблокировать свою учетную запись (`banned = true`) или изменить свою роль на `customer`/`manager`, сервер выбрасывает `ConflictError` (HTTP 409), предотвращая блокировку системы.
2. **Почему при удалении категорий, брендов и промокодов используются разные политики удаления?**
   *Ответ:* Для сохранения ссылочной целостности базы данных: непустую категорию или бренд с привязанными товарами удалить нельзя (требуется переместить товары или скрыть категорию `isVisible = false`). Промокод, если он уже применялся в заказах (`usedCount > 0`), деактивируется (`isActive = false`) вместо физического удаления, сохраняя снимок промокода в истории заказов.
3. **Как обеспечивается разграничение доступа между администратором и менеджером в разделах T11?**
   *Ответ:* Страницы справочников защищены серверным гардом `requireRole('admin')`, а эндпоинты API — `requireApiRole(['admin'], req.headers)`. При попытке менеджера открыть страницу происходит редирект с ошибкой `forbidden`, а при прямом вызове API сервер возвращает `403 Forbidden`. Менеджеру открыт только просмотр каталога для работы с товарами и заказами.
