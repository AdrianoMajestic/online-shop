# AGENT_SPEC.md — ТЗ для ИИ-агента: MVP интернет-магазина

> Положи этот файл в корень репозитория (и продублируй как `CLAUDE.md` / `AGENTS.md` / `.cursorrules`, смотря чем работаешь).
> Исходное ТЗ заказчика лежит рядом: `TZ.md`. Если этот файл и исходное ТЗ расходятся, **приоритет у этого файла**, а расхождение записывается в `TZ_ISSUES.md`.
> Запуск задачи: «Выполни задачу T03 из AGENT_SPEC.md».

## 0. Контекст и цель

Учебный проект: реализовать **MVP** интернет-магазина по техническому заданию заказчика (ООО «ТехноТорг», проект «Кабачок»). Параллельно ведётся **критика ТЗ**: каждая неясность, противоречие или пробел, на которые ты наткнулся при реализации, фиксируется в `TZ_ISSUES.md`.

Разработчик (пользователь) должен уметь **объяснить каждый этап и каждое решение**. Поэтому код должен быть простым, читаемым и без «магии», а после каждой задачи ты пишешь короткое объяснение (см. п. 2.6).

Срок всего проекта: меньше недели. Не усложняй. Лучше меньше функций, но рабочих и протестированных.

## 1. Зафиксированный стек (не менять без запроса)

| Слой | Технология |
|---|---|
| Фреймворк | Next.js 14+ (App Router), React 18, **TypeScript strict** |
| API | Route Handlers в `app/api/**` (REST, JSON) |
| БД | **MongoDB 7 + Mongoose 8** |
| Валидация | zod (на всех входах API и форм) |
| Авторизация | Better Auth (email + пароль, сессии в httpOnly-cookie, `mongodbAdapter`, плагин `admin` для ролей; хэширование паролей встроенное, scrypt) |
| UI | Tailwind CSS + shadcn/ui, lucide-react |
| Состояние на клиенте | React state + context; для запросов `fetch` (SWR/TanStack Query по желанию, но один выбор на весь проект) |
| Тесты | Vitest, только unit-тесты чистой бизнес-логики (цены, промокоды, переходы статусов заказа). Всё остальное проверяется вручную по шагам «Как проверить» |
| Окружение | Без Docker: `npm run dev` + MongoDB Atlas (бесплатный кластер M0, это уже replica set) или локальный `mongod --replSet rs0` |
| Качество | ESLint + Prettier, `tsc --noEmit` без ошибок |

**Важно про MongoDB:** транзакции работают только на replica set. Atlas M0 это даёт из коробки; локально нужен `mongod --replSet rs0` и разовый `rs.initiate()`. Многодокументные операции заказа выполняются в транзакции (`session.withTransaction`). Если транзакции поднять не удалось, запасной вариант: условные атомарные обновления без транзакции плюс компенсация (вернуть остаток при ошибке); это записывается в `DECISIONS.md`.

## 2. Правила работы агента

1. **Одна задача за раз.** Делай только ту задачу (T00–T16), которую назвал пользователь. После выполнения остановись и отчитайся. Не начинай следующую сама и не «улучшай заодно».
2. **Не расширяй скоуп.** Всё, что в разделе 8 «Вне MVP», не реализуется, даже если «это быстро».
3. **Неясность в ТЗ.** Если нужное решение уже есть в разделе 5 (допущения A-xx), используй его. Если нет, выбери самый простой вариант, **запиши допущение** в `docs/DECISIONS.md` и проблему в `docs/TZ_ISSUES.md`, и продолжай. Спрашивай пользователя только если два варианта ведут к разной структуре данных.
4. **Цены, остатки, права, итоговые суммы считаются только на сервере.** Клиенту не доверяем.
5. **Коммиты** маленькие, формат: `feat(T05): серверная корзина и слияние при входе [req 6, 21]`. В скобках номера требований ТЗ.
6. **Объяснение для защиты.** После каждой задачи создай `docs/explain/Txx.md` (до 25 строк): что сделано, почему так, где в коде ключевые места (пути файлов), 3 вопроса, которые могут задать на защите, и ответы на них.
7. **Документы, которые обновляются в каждой задаче:** `docs/TRACEABILITY.md` (требование → задача → файлы → статус), `docs/DECISIONS.md` (решение, причина, альтернатива), `docs/TZ_ISSUES.md` (замечания к ТЗ).
8. **Не добавляй зависимости без нужды.** Новая библиотека: одна строка обоснования в `DECISIONS.md`.
9. **Секреты** только через `.env` (в репозитории только `.env.example`).
10. **Язык:** код, имена, коммиты на английском. Интерфейс магазина, тексты ошибок для пользователя и документация на русском.

## 4. Модель данных (Mongoose)

Исходное ТЗ написано под реляционную БД (3NF, PostgreSQL). Для MongoDB делаем осознанное отступление: **ссылаемся по `ObjectId` там, где данные живут своей жизнью, и встраиваем то, что должно быть зафиксировано** (снимок заказа). Это записывается как решение D-001 в `DECISIONS.md`.

Во всех коллекциях: `timestamps: true` (`createdAt`, `updatedAt`). Мягкое удаление (`deletedAt`) для `User`, `Product`, `Order`.

**User** (коллекции `user`, `session`, `account` ведёт Better Auth, свою схему не пишем): стандартные поля библиотеки (`email`, `name`, `role` из плагина `admin`: `customer | manager | admin`) плюс дополнительные поля (`additionalFields`): `phone`, `assignedCategoryIds[]` (для менеджера), `consents: { personalData: {given, at}, marketing: {given, at} }`, `deletedAt`. Блокировка пользователя через средства плагина `admin` (ban).
*Гость не хранится в БД: это отсутствие сессии.*

**Category**: `parentId` (nullable), `title`, `slug` (unique), `description`, `isVisible`, `sortOrder`.

**Brand**: `title`, `slug` (unique), `logoUrl`, `description`.

**Product**: `categoryId`, `brandId`, `sku` (unique), `title`, `slug` (unique), `description`, `price`, `discountPrice` (nullable), `stockQuantity`, `isPublished`, `images[]` (url, alt), `attributes[]` (`{key, value}`), `ratingAvg`, `reviewsCount`, `salesCount`, `deletedAt`.
Индексы: text по `title`, `description`; `sku`; `categoryId`; `brandId`; `price`.

**Address**: `userId`, `city`, `street`, `house`, `apartment`, `postalCode`, `comment`.

**DeliveryMethod**: `code`, `title`, `price`, `description`, `isActive`.

**PromoCode**: `code` (unique, uppercase), `discountType` (`percentage | fixed`), `discountValue`, `minOrderAmount`, `validFrom`, `validTo`, `usageLimit`, `usedCount`, `isActive`.

**Cart** (только для авторизованных): `userId` (unique), `items[]` (`{productId, quantity}`).

**Order**:
- `number` (человекочитаемый, уникальный), `userId` (nullable для гостя)
- `contact: {fullName, phone, email}` (снимок, обязателен всегда)
- `shippingAddress` (встроенный снимок: city, street, house, apartment, postalCode, comment)
- `delivery: {methodId, title, price}` (снимок)
- `items[]`: `{productId, sku, title, quantity, pricePerUnit, totalPrice}` (снимок цены на момент покупки)
- `promo: {promoCodeId, code, discountAmount}` (nullable)
- `totalAmount` (сумма товаров), `discountAmount`, `deliveryCost`, `finalAmount`
- `status`, `paymentMethod` (`card_online | cod`), `customerComment`, `managerComments[]` (`{authorId, text, at}`), `statusHistory[]` (`{from, to, byUserId, at}`)

**Payment**: `orderId`, `provider` (`mock`), `externalPaymentId` (unique), `method`, `status` (`pending | succeeded | failed | refunded`), `amount`, `paidAt`.

**Review**: `userId`, `productId`, `rating` (1–5), `comment`, `isApproved`, `managerReply: {authorId, text, at}`. Уникальный индекс `(userId, productId)`.

**AuditLog**: `userId`, `action`, `entity`, `entityId`, `meta`, `ip`, `at`.

## 5. Допущения, закрывающие пробелы ТЗ

Это решения по неясным местам ТЗ. Их можно менять только по решению пользователя. Каждое должно быть отражено в `docs/TZ_ISSUES.md`.

| № | Пробел в ТЗ | Принятое решение |
|---|---|---|
| A-01 | Название: «Кабан/Кабанчик/Кабачок» | Используем «Кабачок» (так в большинстве мест) |
| A-02 | Вход: email, логин или телефон | Только email + пароль |
| A-03 | Токены: access + refresh | Сессии Better Auth (httpOnly-cookie, срок и ротация настраиваются библиотекой). Свой JWT не пишем |
| A-04 | Гостевой заказ: `Order.userId` и `Address` привязаны к пользователю | `contact` и `shippingAddress` встроены в заказ; `userId` nullable |
| A-05 | Статусы заказа неполные (нет «оплачен») | `new → paid → processing → shipped → completed`; `cancelled` из `new/paid/processing`. Переходы в `lib/order-status.ts` |
| A-06 | Когда списывается остаток | При создании заказа, атомарно. При отмене возвращается |
| A-07 | Итоговая сумма не учитывает доставку | `finalAmount = totalAmount − discountAmount + deliveryCost` |
| A-08 | Порядок скидки и промокода | В `totalAmount` берётся `discountPrice ?? price`; промокод применяется поверх к сумме товаров |
| A-09 | Видимость заказов менеджера | Менеджер видит все заказы, но редактирует товары только в назначенных категориях |
| A-10 | Кто модерирует отзывы | Менеджер и админ |
| A-11 | Отмена заказа покупателем | Разрешена только в статусе `new` |
| A-12 | Способы оплаты | `card_online` (мок-провайдер) и `cod` (при получении). СБП и счёт для юрлиц вне MVP |
| A-13 | Интеграция со службами доставки | Справочник `DeliveryMethod` с фиксированной ценой. API СДЭК вне MVP |
| A-14 | Хранение избранного и корзины в Redis | Redis не используем. Корзина пользователя в Mongo, гостя в `localStorage` |
| A-15 | Пересечение «мягкое удаление» и «право на удаление ПДн» | В MVP только мягкое удаление; анонимизация вне MVP |
| A-16 | Атрибуты товара: JSON-поле против «управления атрибутами» (№49) | Массив `{key, value}` в товаре. Справочник атрибутов вне MVP |
| A-17 | Отзыв «на купленный товар» | Разрешён, если у пользователя есть заказ со статусом `completed` с этим товаром |
| A-18 | Уведомления Email/SMS/Telegram | В MVP письма не отправляются: пишем событие в лог (`console` + `AuditLog`). Mailpit опционально |

## 6. Единые соглашения API

- Базовый путь `/api`, JSON, коды: 200/201, 400 (валидация), 401, 403, 404, 409 (конфликт, например нет остатка), 500.
- Формат ошибки: `{ "error": { "code": "OUT_OF_STOCK", "message": "Недостаточно товара", "details": {} } }`.
- Пагинация: `?page=1&limit=20` → `{ items, page, limit, total }`.
- Деньги: целые числа в **копейках** в БД и API, форматирование `1 234,56 ₽` только в UI.
- Авторизация: сессия Better Auth в httpOnly-cookie. Хелперы `requireAuth()`, `requireRole(...roles)` в `lib/rbac.ts` работают поверх `auth.api.getSession({ headers })`.
- Ошибка входа всегда «Неверный логин или пароль» (не раскрываем, существует ли аккаунт).

## 7. Задачи

Каждая задача: **цель → требования ТЗ → что сделать → критерии приёмки (DoD)**. Общее DoD для всех: `npm run typecheck`, `npm run lint`, `npm test` (unit-тесты) проходят, задача проверена руками по шагам «Как проверить»; обновлены `TRACEABILITY.md`, `DECISIONS.md`, `TZ_ISSUES.md`; создан `docs/explain/Txx.md`.

### Блок A. Основа

**T00. Каркас проекта**
- Создать Next.js + TS strict + Tailwind + shadcn/ui, ESLint/Prettier, скрипты `dev`, `build`, `typecheck`, `lint`, `test`, `seed`.
- `.env.example` (`MONGODB_URI`, `BETTER_AUTH_SECRET`, `BETTER_AUTH_URL`, `PAYMENT_WEBHOOK_SECRET`); в README описать, как поднять Mongo (Atlas M0 или локально как replica set).
- Создать `docs/` со всеми файлами-заготовками. Скопировать исходное ТЗ в `docs/TZ.md`.
- Общий слой: `lib/db.ts` (кэшированное подключение), `lib/errors.ts` (типизированные ошибки и обработчик для route handler'ов).
- **DoD:** `npm run dev` стартует приложение и подключается к Mongo, на `/` пустая страница с хедером и футером, `/api/health` возвращает `{ok:true, db:true}`.

**T01. Модели и seed**
- Требования: раздел 6 ТЗ. Реализовать все схемы из п. 4 с индексами и валидацией.
- `scripts/seed.ts`: (пользователей добавляет T02 через API Better Auth) 6 категорий (2 уровня вложенности), 5 брендов, ~30 товаров с атрибутами и остатками, 3 способа доставки, 2 промокода, несколько отзывов.
- `docs/ER.md` с диаграммой Mermaid.
- **DoD:** `npm run seed` идемпотентен (повторный запуск не плодит дубли).

**T02. Авторизация и роли (Better Auth)**
- Требования: №9, 10, 31 (согласие ПДн при регистрации).
- Подключить Better Auth: `lib/auth.ts` (конфиг с `mongodbAdapter`, `emailAndPassword: { enabled: true }`, плагин `admin` с ролями `customer | manager | admin`, роль по умолчанию `customer`), route handler `app/api/auth/[...all]/route.ts`, клиент `lib/auth-client.ts`. Точные имена опций сверять с актуальной документацией Better Auth, не выдумывать.
- Дополнительные поля пользователя (`additionalFields`): `phone`, `assignedCategoryIds`, `consents`, `deletedAt`.
- Регистрация: email, имя, телефон, пароль + подтверждение, обязательный чекбокс согласия на ПДн (без него регистрация невозможна, проверка на сервере, не только в форме). Пароль ≥ 8 символов, буквы и цифры. Хэширует библиотека.
- Ошибка входа всегда с одним текстом «Неверный логин или пароль». Встроенный rate limit Better Auth включить для входа.
- `lib/rbac.ts`: `requireAuth()`, `requireRole(...roles)`; защита `/admin/**` и `/account/**` проверкой сессии на сервере (в layout), а не только в middleware.
- Seed пользователей (в `scripts/seed.ts`): `admin@shop.test`, `manager@shop.test`, `user@shop.test`, пароль `Passw0rd1`. Создавать через API Better Auth (чтобы пароль был захэширован правильно), потом назначать роли; менеджеру назначить 2 категории.
- UI: страницы/модалки входа и регистрации, меню пользователя в хедере.
- **DoD:** руками: регистрация, дубль email, неверный пароль (одинаковое сообщение), customer на `/admin` получает редирект или 403, выход из системы.

### Блок B. Витрина

**T03. API каталога**
- Требования: №2, 3, 4, 5.
- `GET /api/categories` (дерево), `GET /api/products` с параметрами: `q`, `category` (slug, включая потомков), `brand` (мультивыбор), `priceMin`, `priceMax`, `sort` (`popular | price_asc | price_desc | new | rating`), `page`, `limit`. `GET /api/products/[slug]`.
- Поиск: text-индекс + точное/префиксное совпадение по `sku`. Только `isPublished && !deletedAt`.
- **DoD:** руками: комбинация 3+ фильтров, поиск по SKU, сортировка, пагинация.

**T04. UI каталога**
- Требования: №1, 2, 3, 4, 5, 12–15 (статические страницы «О компании», «Доставка», «Оплата», «Контакты»).
- Страницы: главная (баннер-заглушка, популярные категории, «Хиты продаж» по `salesCount`, «Новинки»), каталог (хлебные крошки, фильтры, сортировка, сетка, пагинация, URL отражает фильтры), карточка товара (галерея, SKU, цена и старая цена, наличие, атрибуты, кнопка «В корзину»), кастомная 404. Метаданные `title/description`, Schema.org `Product` в карточке.
- Серверный рендеринг для каталога и карточки.
- **DoD:** адаптив 320–1920 px, фильтры меняют URL и работают без полной перезагрузки, Lighthouse Performance на главной ≥ 80 (замер зафиксировать в `explain/T04.md`).

**T05. Корзина**
- Требования: №6, 21.
- Гость: корзина в `localStorage`. Пользователь: `GET/PUT /api/cart`. При входе гостевая корзина **сливается** с серверной (количества суммируются, но не больше остатка).
- UI: иконка со счётчиком в хедере, страница корзины (изменить количество, удалить, промежуточная сумма). Пустая корзина: блок с рекомендациями.
- Цены в корзине подтягиваются с сервера по `productId` (не хранятся на клиенте).
- **DoD:** руками: слияние гостевой и серверной корзин при входе; нельзя добавить больше остатка.

**T06. Оформление заказа и создание заказа**
- Требования: №11, 18, 31, раздел 5.1.8.
- `GET /api/delivery-methods`, `POST /api/promo/validate`, `POST /api/orders`.
- Checkout (одностраничный с секциями): контакты, адрес (для авторизованных выбор из сохранённых или новый), способ доставки, способ оплаты (`card_online`/`cod`), промокод, комментарий. Работает и для гостя.
- Сервис `createOrder` в **транзакции**: загрузка товаров → проверка `isPublished` и остатка → атомарное списание `updateOne({_id, stockQuantity: {$gte: q}}, {$inc: {stockQuantity: -q}})` → расчёт сумм в `lib/pricing.ts` → применение промокода (атомарный инкремент `usedCount` с проверкой лимита и сроков) → создание `Order` со снимками → `Payment(pending)` для онлайн-оплаты. Номер заказа генерируется на сервере.
- **DoD:** unit-тесты на `lib/pricing.ts` (процентный и фиксированный промокод, `minOrderAmount`, истёкший, лимит, итоговая сумма с доставкой). Руками: гостевой заказ; нехватка остатка (409, остатки не изменились); два заказа на последний товар подряд (успешен только один).

**T07. Оплата (мок-провайдер)**
- Требования: №60 (в упрощённом виде).
- Интерфейс `PaymentProvider` (`createPayment`, `verifyWebhook`), реализация `MockProvider`. Страница `/pay/mock/[paymentId]` с кнопками «Оплатить» и «Отклонить», которые вызывают `POST /api/payments/webhook`.
- Вебхук: проверка HMAC-подписи, **идемпотентность** (повторный вызов с тем же событием ничего не меняет), успех → `Payment.succeeded`, `Order.status = paid`, `salesCount++` у товаров; отказ → `Payment.failed`, заказ остаётся `new`, можно создать новую попытку оплаты.
- Страница «Спасибо за заказ» с номером и составом.
- **DoD:** руками (curl или страница мока): неверная подпись отклоняется, повтор события ничего не меняет, успех и отказ, повторная оплата после отказа.

**T08. Личный кабинет**
- Требования: №16, 17, 18, 19, 20, 26, 27, 30, 31.
- `/account`: профиль (просмотр, редактирование, смена пароля), адреса (добавить, изменить, удалить), мои заказы (список с фильтром по статусу, детальная страница с историей статусов), «повторить заказ» (добавляет товары в корзину с учётом наличия), отмена заказа в статусе `new` (A-11), управление согласиями (ПДн и рассылка). Отзыв на ПДн нельзя «тихо» сбросить: показывать предупреждение об ограничении функций.
- **DoD:** пользователь видит только свои заказы и адреса (проверить руками: чужой заказ → 404/403).

### Блок C. Админка

**T09. Админка: товары**
- Требования: №35–39, раздел 5.1.10.
- `/admin/products`: список с поиском и фильтрами, создание, редактирование, деактивация (`isPublished=false`, без удаления), изменение цены и остатка, загрузка изображений по URL.
- Менеджер видит и меняет только товары своих категорий (проверка на сервере, не только в UI). Админ видит всё.
- **DoD:** руками: менеджер получает 403 при изменении товара чужой категории.

**T10. Админка: заказы**
- Требования: №32, 33, 34.
- `/admin/orders`: список с фильтрами (статус, дата, поиск по номеру/email), карточка заказа, смена статуса только по разрешённым переходам (`lib/order-status.ts`), комментарии менеджера, запись в `statusHistory`. Отмена возвращает остаток.
- При смене статуса пишется «уведомление» в лог (A-18).
- **DoD:** unit-тест таблицы переходов (все допустимые и недопустимые пары); возврат остатка при отмене проверен руками.

**T11. Админка: справочники, пользователи, доставка, промокоды**
- Требования: №44–48, 51, 52 (+ №50 в виде включения/отключения способов оплаты).
- CRUD категорий (дерево), брендов, способов доставки, промокодов. Управление пользователями: список, блокировка (`isActive`), смена роли, назначение категорий менеджеру.
- Защита: админ не может снять роль админа у самого себя.
- **DoD:** все эндпоинты закрыты `requireRole('admin')`; менеджер получает 403 (проверено руками).

**T12. Журнал аудита**
- Требование: №62 (минимально).
- Хелпер `audit(action, entity, entityId, meta)`; вызывается при входе, смене статуса заказа, изменении цены и остатка, удалении/деактивации, смене роли. Страница `/admin/audit` (только админ) со списком и фильтром.
- **DoD:** при изменении цены в админке появляется запись с IP и временем.
